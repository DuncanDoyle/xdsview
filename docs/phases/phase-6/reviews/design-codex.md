### P1 — Correctness

- **The table treats an invalid `FilterConfig` as enabling a filter.** Envoy rejects a wrapper with `disabled: false` or omitted `disabled` when `config` is absent. An explicit `config: {}` enables the filter. Distinguish those cases before turning “any other” into a test expectation. The route → virtual host → route configuration precedence is correct for enablement when there is no weighted-cluster override. `docs/phases/phase-6/design.md:32` · [Envoy config parsing](https://github.com/envoyproxy/envoy/blob/c7c57d8f48/source/common/router/per_filter_config.cc#L82-L122) · [Envoy precedence](https://github.com/envoyproxy/envoy/blob/c7c57d8f48/source/common/router/config_impl.cc#L1438-L1443)
- **The output can present a conditional chain as definitive.** The selected weighted cluster can override `filterDisabled`. Excluding its resolution is a reasonable scope decision, but `Runs` and the text still read as definitive and the renderer specifies no warning. Label the result as the baseline before backend selection whenever the flag is set. The same paragraph also incorrectly rules out upstream route switches. Envoy passes route-aware callbacks when building the router’s upstream chain, and a cluster-specific chain can supersede it. Label the upstream list as router configuration. `docs/phases/phase-6/design.md:43` · [Weighted-cluster override](https://github.com/envoyproxy/envoy/blob/c7c57d8f48/source/common/router/weighted_cluster_specifier.cc#L235-L245) · [Upstream chain selection](https://github.com/envoyproxy/envoy/blob/c7c57d8f48/source/common/router/upstream_request.cc#L155-L184) · [Route-aware callback](https://github.com/envoyproxy/envoy/blob/c7c57d8f48/source/common/http/filter_manager.h#L1073-L1077)

### P2 — Design or plan

- **Listener diagnostics can disappear from kgwctl’s route view.** Active-first selection matches Envoy’s state model, but the text contract only specifies the primary state and error, leaving active-plus-warming and active-plus-draining invisible. Envoy also emits unnamed LDS-wide errors, which need a diagnostic representation. More directly, current narrowing drops every listener without a matching route, including rejected listeners. kgwctl’s design requires those diagnostics to survive and selection to use resolved origins. Assign both behaviors to an owner before declaring E11 complete. `docs/phases/phase-6/design.md:70` · `pkg/envoy/filter/filter.go:85` · kgwctl design.md:84 (`kgwctl/docs/phases/phase-3/design.md:84`) · [Envoy listener dump](https://github.com/envoyproxy/envoy/blob/c7c57d8f48/source/common/listener_manager/listener_manager_impl.cc#L555-L599)
- **The response-order API overstates what the model knows.** `Response()` reverses every enabled entry. Envoy reverses encoder filters, and kgwctl explicitly requires encoder capability or an unknown result. The per-HCM route model serves both consumers, but the shared API needs either capability information or an explicitly named reverse configuration order. The same distinction applies to decoder participation and `Runs`. `docs/phases/phase-6/design.md:82` · kgwctl design.md:56 (`kgwctl/docs/phases/phase-3/design.md:56`) · [Envoy filter ordering](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/http_filters#filter-ordering)
- **The renderer’s dependency contract contradicts its fallback.** `render` promises stdlib plus `model`, but `Text` calls `chain.Effective`, pulling in `chain` and `origin`. The existing D-004 test allows those core imports and already rejects Charmbracelet and `source/kube`. Decide whether annotation is a caller precondition or the renderer may depend on the wider core. The public `Cursor` and `Expand` hooks also make krp’s interaction model part of the exported API. `docs/phases/phase-6/design.md:138` · `pkg/envoy/boundary_test.go:17`
- **Two integration paths can silently lose the new data.** The parser’s RDS clone reconstructs both structs field by field, so the new maps must survive the join into the HCM. Separately, the plan annotates `krp dump` text only, while the design promises `effectiveChain` in `-o json`. Cover the joined snapshot and the JSON command boundary explicitly. `docs/phases/phase-6/implementation-plan.md:22` · `pkg/envoy/parser/parser.go:571` · `docs/phases/phase-6/implementation-plan.md:42` · `docs/phases/phase-6/design.md:194`

### P3 — Test gaps

- **The TUI tests need to prove navigation through the new output.** The current cursor enumerates every HCM filter, but the proposed default collapses disabled filters into a summary. Press through an enabled/disabled/enabled sequence and verify the visible selection and expanded config, including a vhost override. Ref-list and ANSI-marker tests alone can pass while a cursor position has no visible row. `docs/phases/phase-6/implementation-plan.md:41` · `internal/tui/tui.go:36`
- **The live auth check lacks a reliable oracle.** Scenario `03` has no ext_authz service endpoints. A denied request alone cannot establish that ext_authz produced the response. Assert an ext_authz-specific stat or response detail against a control route, or use a responding auth service with deterministic allow and deny outcomes. `docs/phases/phase-6/implementation-plan.md:47` · Scenario 03 README.md:3 (`testdata/scenarios/03-multi-policy/README.md:3`)

### P4 — Later-phase fragility

- **Phase 7 needs a comparison boundary for the new fields.** Phase 5 already excludes mapper-derived origins from configuration equality. Extend that rule to `effectiveChain` and distinguish listener lifecycle metadata from configuration. `PerBackendFilterConfig` also reduces all backend overrides to one bit, so a change between two non-empty overrides will require the underlying config to detect. `docs/phases/phase-6/design.md:76` · Phase 5 design.md:193 (`docs/phases/phase-5/design.md:193`) · `docs/roadmap.md:80`
