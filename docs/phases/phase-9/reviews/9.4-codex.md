### P1

- **P1 · correctness · ECDS can attach another subscription’s config.** The parser joins on name and allowed type. Envoy keys subscriptions by config source and name, and dumps downstream and upstream HTTP filters separately. If only one of two same-name, same-type subscriptions has received a config, krp can show it running in both slots. `pkg/envoy/parser/parser.go:567` · Envoy subscription lookup `envoy/source/common/filter/config_discovery_impl.cc:226`
- **P1 · correctness · ECDS skips valid filter configurations.** A network HCM supplied through `config_discovery` is never resolved. An HTTP router resolved through ECDS or its default is recognized, but upstream filters are read from the original, empty `hf.TypedConfig`. Both paths can omit installed filter slots. `pkg/envoy/parser/parser.go:401` · `pkg/envoy/parser/parser.go:539` · Envoy listener filter proto `envoy/api/envoy/config/listener/v3/listener_components.proto:39`
- **P1 · correctness · Partial captures can falsely report an ECDS default as running.** A malformed ECDS entry is skipped, after which an active listener’s default is treated as installed. The same happens with a filtered file that omits the installed entry. Absence in either case leaves the installed config unknown under P-010 rule 3. `pkg/envoy/parser/parser.go:258` · `pkg/envoy/parser/parser.go:578`
- **P1 · correctness · Bootstrap listeners can trigger a false `rds-missing`.** The parser marks every static listener active. Envoy emits static entries before checking whether workers have started, so a complete startup dump can contain a static HCM still waiting for RDS. `pkg/envoy/parser/parser.go:353` · Envoy listener dump `envoy/source/common/listener_manager/listener_manager_impl.cc:541`
- **P1 · correctness · Default-chain output shows an SNI condition Envoy ignores.** The default chain goes through the ordinary `server_names` parser and renderer. Envoy uses it as the fallback regardless of its `filter_chain_match`, so the output can imply a narrower fallback than Envoy applies. `pkg/envoy/parser/parser.go:377` · Envoy listener proto `envoy/api/envoy/config/listener/v3/listener.proto:255`
- **P1 · correctness · Empty legacy `exact_match` is reported as empty-string equality.** Envoy’s deprecated top-level form matches any header value when the configured string is empty. The parser collapses it into the same representation as `string_match.exact: ""`, which really does require an empty value. `pkg/envoy/parser/parser.go:1201` · Envoy header matcher `envoy/source/common/http/header_utility.h:182`

### P2 and P3

- **P2 · architecture · `Reported` needs an explicit contract for `v1alpha2`.** The sampled golden emits `reported: RS1` and `reported: RS0` after removing those IDs from the source list. If a selected route retains such a source, pruning preserves the dangling value, conflicting with 9.3’s requirement that IDs outside `selection` resolve in the snapshot. Scenario 00 golden `testdata/golden/scenarios/00-simple/kgateway-v2.5.0.json:437` · 9.3 acceptance `docs/phases/phase-9/implementation-plan.md:54`
- **P2 · correctness · JSON drops ECDS run state when the HCM has no resolved route config.** `Effective` computes a chain keyed by the route-config use and text prints it. JSON attaches chains only to routes, so an unresolved slot under a missing-RDS or scoped HCM has no `Runs` or `State` in the output. `pkg/envoy/chain/chain.go:41` · `cmd/krp/output.go:59`
- **P3 · correctness · The ECDS tests miss the ambiguity deviation.** No case has two entries with the same name and allowed type. A first-wins resolver would pass the current tests, which never require `ecds-ambiguous` and an unresolved slot together. `pkg/envoy/parser/correctness_test.go:189`
